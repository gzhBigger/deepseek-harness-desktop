# Agent Note: 随包 DSH 运行时升级到 0.2.2-rc.2

Status: implemented

> 部分取代 [手机首屏瘦身](2026-10-29-phone-first-load-slimming.md)：0.2.2 上游已把 8 张引导插画作为独立资源发出，
> 本文删掉了桌面壳的外置路由与构建期改写；瘦身目标由上游实现。
> 上一轮运行时记录见 [0.2.1-rc.2](2026-10-18-dsh-runtime-0-2-1-rc2.md)。

## Problem

用户要求把桌面端随包 dsh 从 `0.2.1-rc.2` 升到 `0.2.2-rc.2`，并先解决已装插件的冲突；明确说明**先不要发版**，
等他确认。真正卡住的不是壳，而是用户 profile 里的 `dsh-ops@0.5.4`：

- `engines.dsh` 是 `>=0.2.2-rc.1 <0.2.3-0`，peer 还要求 `@deepseek-ai/cordis ~4.1.0` 与
  `@deepseek-ai/dsh >=0.2.2-rc.1 <0.2.3-0`；运行时 `0.2.1-rc.2` 带的是 cordis 4.0.5，兼容性检查直接跳过它。
- 0.2.2 同时带来一批 Client API 破坏性变更（右键菜单 target、CSS 锚点菜单、窗口拖拽区域、终端 bundle、
  `BundleInfo.updatable` 等），必须确认随包插件没有踩中。
- 0.2.2 还把 settings-account 的 8 张 onboarding webp 从 base64 内联改成了真实资源；壳在 0.2.1 时代为手机首屏
  做的 bundle 改写因此失效，`prepare-runtime` 会在「找不到内联 webp」处失败。

## Decision

**把 `electron/runtime-pin.json` 的 `dsh` 升到 `0.2.2-rc.2`，重建运行时；删除壳的 onboarding 外置机制，
让上游资源直接随包；不发布，等用户确认。**

- `runtime-pin.json` 只改 dsh；pnpm 11.7.0、node 24.22.2 不动。壳版本仍是 0.4.24，发布前必须另行递增。
- `prepare-runtime` 不再调用 `patchOnboardingAssets`，改为断言 settings-account 的 `client.js` 不含
  `data:image/webp;base64,`。失败信息要求恢复外置步骤；成功日志为「引导插画由上游外置，无需改写 bundle」。
- 删除 `electron/src/onboarding-assets.ts`、`onboarding-assets.test.ts`，以及
  `electron/resources/dsh-desktop-shell/onboarding/` 下的 8 张旧图。
- 删除桌面壳插件的 `/dsh-desktop-shell/v1/onboarding/` 路由、`serveOnboardingAsset()` 与相关常量/import；
  注册日志改为「ping 匿名，其余需 DSH 会话认证」。
- `verify-package` 改成校验上游资源：bundle 不得退回 base64；从 bundle 提取 `onboarding-*.webp` 引用，必须恰好
  8 个；逐个用 `app.asar` 的 `readFile` 确认文件存在且非空。
- 没有改桌面壳的 Client API：搜索随包插件与 `dsh-desktop-shell`，`useAnchoredPosition`、`AnchoredPositionOptions`、
  `getAnchorRect`、`MenuTarget`、`useMenuTarget`、`menuTarget`、`ctx.menus`、`MenuTargetMap`、
  `contextMenuTrigger`、`menuPoint`、`updatable`、`BundleInfo`、`app-region`/`no-drag`、
  `optional-terminal-bash`/`optional-terminal-pwsh` 均无命中。
- Electron 子进程继续用 `--expose-internals`；这是随包 `node-addon-require-builtin` 替身的要求，0.2.2 没变。
  手动用普通 node 跑运行时也必须带这个 flag，否则报
  `node-addon-require-builtin (stub): cannot load internal/modules/esm/loader`。

## Verification

- **运行时重建**：`pnpm runtime:prepare` 成功，清单为
  `{"shell":"0.4.24","dsh":"0.2.2-rc.2","files":33169,"bytes":826932064}`；关键文件 29 个，需物理落盘 487 个。
  裁剪 47,052 项 / 440.3 MiB（1,139.4 MiB → 699.0 MiB）。
- **真实 profile（普通 node）**：`node --expose-internals ... --profile dsh-desktop --host 127.0.0.1 --port 41741`
  启动成功，认证后页面包含 `dsh-ops`、`billion-context`、`genui`，说明 dsh-ops 0.5.4 的硬版本冲突已解决。
- **桌面壳 overlay（Electron Node 模式）**：
  `ELECTRON_RUN_AS_NODE=1 electron.exe --expose-internals ... --profile dsh-desktop --patch ... --port 41742`
  打印 `dsh web:` 认证地址，日志出现 `[dsh-desktop-shell] host apply` 与路由注册，页面正常。
- **dev 壳 60 秒超时不是运行时缺陷**：`dsh-desktop-dev` 的 `cordis.patch.yml` 配了故意失败/缺环境的 MCP fixture
  （`npx @raviraj87/jenkins-mcp` 缺 JENKINS_URL、`definitely-not-a-real-binary-xyz`、指向不存在的本地
  jenkins-mcp 入口），每 30 秒重试，把认证地址拖到 60 秒之后。release profile 没有这些 fixture。
- **测试**：`npm test` 663 条 / 655 通过 / 8 跳过 / 0 失败；`npm run build` 成功。
- **打包校验**：`npm run package:dir` 成功，`verify-package` 通过（Electron 44.10.0、asar 内 33,170 个文件、
  关键文件 29 个、物理落盘 487 个、pnpm 11.7.0 shim/node 直跑均通过）。尚未构建 NSIS 安装包。
  0.2.2 会额外产生一条上游警告 `@deepseek-ai/dsh-client-ui-account-notifications: pending (waiting for
  service: accountUi)`；`verify-package` 现在只把「警告块里出现随壳插件名」或 `failed to import` 当作失败，
  避免把上游等待服务误判成插件没激活。

## Alternatives considered

- **留在 0.2.1-rc.2，只给 dsh-ops 加 `compatibility.json` 精确豁免**（最强理由：不升运行时、不动 218 MB 安装包、
  风险最小）→ 弃：豁免只绕过兼容性检查，dsh-ops 0.5.4 要的 cordis `~4.1.0` 与运行时 4.0.5 不是同一套 API；
  跳过检查后插件仍会在真实加载时坏掉，等于把确定性失败推迟到用户机器。
- **继续保留 onboarding 外置改写**（最强理由：手机首屏瘦身效果已经被验证，少改代码）→ 弃：0.2.2 的
  `client.js` 已不再内联 base64，改写函数会以「找不到 8 张 webp」失败；上游已经用真实资源解决了同一个问题，
  继续维护两套路由只会增加漂移。
- **先裁剪运行时体积再升级**（强理由：33,169 文件 / 788.6 MiB 比 0.2.1 多约 218 MB，安装包会明显变大）→ 暂缓：
  0.2.2 新增的 cua/official-bundles 依赖里有真实运行期文件，贸然裁剪会把「能启动」变成「启动后缺文件」；
  先用完整树完成集成验证，体积优化留给独立的裁剪决定。
- **不回退，直接发版**（强理由：用户已经等了一段时间）→ 弃：用户明确说「先不要发版，等我确认」，且安装包
  还没跑 `verify-package`；发版前必须补版本号与打包验证。

## Consequences

- 运行时从 24,244 文件 / 570,237,736 B 涨到 33,169 文件 / 826,932,064 B；安装包和安装时间都会增加，发布前要实测。
- 已装 0.4.24 的用户不会自动获得 0.2.2；必须发一版新壳（运行时随 app.asar 分发，没有 DSH 自更新通道）。
- 桌面壳不再提供 onboarding 路由；Cloudflare 上仍有一条包含
  `/dsh-desktop-shell/v1/onboarding/` 的缓存规则，路径已失效但不会误伤，后续可清理。
- 0.2.2 默认关闭 `fs-observation-policy`，并给 dsh-base / Web standard preset 增加 `apply_patch`；这是上游行为变化，
  用户会感知到 write/edit/apply_patch 不再要求先读，不需要壳适配。
- dev 环境的 MCP fixture 会拖慢启动；如果以后 dev 壳再次报认证超时，先清 fixture 或单独调大超时，不要误判成运行时问题。
